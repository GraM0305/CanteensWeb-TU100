# เอกสารสถาปัตยกรรมระบบ (System Architecture)

## 0. สถานะปัจจุบันของระบบที่ใช้งานจริง

> เนื้อหาในหัวข้อ 1–12 ด้านล่างเป็นสถาปัตยกรรม **เป้าหมายเดิม** (Express + PostgreSQL + เมนูอาหาร)
> ซึ่งไม่ตรงกับระบบที่ deploy อยู่ในปัจจุบัน ให้ใช้หัวข้อนี้เป็นข้อมูลอ้างอิงหลักเมื่อมีข้อขัดแย้ง

| ส่วนประกอบ | ระบบที่ใช้งานจริง | ตำแหน่งในโปรเจกต์ |
|---|---|---|
| Frontend | HTML, CSS, JavaScript (Tailwind และ Leaflet โหลดจาก CDN) เผยแพร่บน Cloudflare Pages (`canteensweb-tu100.pages.dev`) | `frontend/` |
| Backend (production) | Cloudflare Worker ไฟล์เดียว | `backend/cloudflare/index.js` |
| Database (production) | Cloudflare D1 (SQLite) | migration ใน `backend/cloudflare/migrations/` |
| Backend (ใช้พัฒนาในเครื่อง) | Express.js + `pg` (PostgreSQL) | `backend/src/` |
| Database (ใช้พัฒนาในเครื่อง) | PostgreSQL | `database/` |
| การตั้งค่า URL ของ API ฝั่งหน้าเว็บ | ไฟล์เดียว | `frontend/js/config.js` |

ข้อแตกต่างจากเอกสารเป้าหมายด้านล่าง:

- **ไม่มีข้อมูลเมนูอาหาร (Menus)** ไม่มีตาราง และไม่มี endpoint `/api/menus` หรือ `/api/vendors/:id/menus`
- **ไม่มีชั้น Controllers / Services / Repositories** Express ใช้เฉพาะ `routes/` ที่เรียกฐานข้อมูลโดยตรง และ Worker เป็นไฟล์เดียว
- ฐานข้อมูลที่ใช้เผยแพร่จริงคือ D1 ไม่ใช่ PostgreSQL
- Worker ตั้ง `Cache-Control: public, max-age=300` เฉพาะคำตอบที่สำเร็จ และจำกัดคำค้นหา `search` ไม่เกิน 100 ตัวอักษร
- GitHub Actions (`.github/workflows/pages-deployment.yml`) รัน smoke test (`npm test` ใน `backend/`) แล้ว deploy เฉพาะหน้าเว็บขึ้น Cloudflare Pages ส่วน Worker ต้อง deploy เองด้วย `npx wrangler deploy` จาก `backend/cloudflare/`

## 1. ภาพรวมของระบบ (System Overview)

โครงการ CanteensWeb-TU100 เป็นเว็บไซต์สำหรับแสดงข้อมูลโรงอาหาร ร้านค้า และเมนูอาหารภายในมหาวิทยาลัยธรรมศาสตร์ ศูนย์รังสิต

ระบบถูกออกแบบให้แบ่งการทำงานออกเป็น 3 ส่วนหลัก ได้แก่

1. **Frontend** — ส่วนติดต่อกับผู้ใช้งาน ทำหน้าที่แสดงผลเว็บไซต์และรับคำสั่งจากผู้ใช้งาน
2. **Backend** — ส่วนประมวลผลคำขอจาก Frontend ติดต่อฐานข้อมูล และส่งข้อมูลกลับไปแสดงผล
3. **Database** — ส่วนจัดเก็บข้อมูลโรงอาหาร ร้านค้า และเมนูอาหาร

เทคโนโลยีที่ใช้ในระบบมีดังนี้

| ส่วนประกอบ | เทคโนโลยี | หน้าที่ |
|---|---|---|
| Frontend | HTML, CSS, JavaScript | สร้างหน้าเว็บไซต์และจัดการการแสดงผล |
| Backend | Node.js, Express.js | ประมวลผลคำขอและให้บริการ API |
| Database | PostgreSQL | จัดเก็บข้อมูลของระบบ |
| Database Driver | pg | เชื่อมต่อ Backend กับ PostgreSQL |
| Map | Leaflet | แสดงแผนที่และตำแหน่งโรงอาหาร |
| API | REST API | ใช้รับส่งข้อมูลระหว่าง Frontend และ Backend |

## 2. สถาปัตยกรรมการทำงานของระบบ (System Architecture)

ระบบจะใช้รูปแบบ Client-Server Architecture โดยแบ่งหน้าที่ระหว่าง Frontend และ Backend อย่างชัดเจน

### 2.1 ลำดับการทำงานของระบบ

```text
             ผู้ใช้งาน (User)
                    |
                    v
             Frontend
          (HTML / CSS / JS)
                    |
                    | HTTP Request
                    v
              Backend API
          (Node.js + Express)
                    |
                    v
                 Routes
          (กำหนดเส้นทาง API)
                    |
                    v
              Controllers
          (รับและจัดการ Request)
                    |
                    v
                Services
          (ประมวลผลตามเงื่อนไข)
                    |
                    v
              Repositories
          (ติดต่อฐานข้อมูล)
                    |
                    v
              PostgreSQL
             (จัดเก็บข้อมูล)
```

เมื่อ Backend ได้รับข้อมูลจากฐานข้อมูลแล้ว จะส่งผลลัพธ์ย้อนกลับไปยัง Frontend ในรูปแบบ JSON เพื่อให้เว็บไซต์นำไปแสดงผลแก่ผู้ใช้งาน

### 2.2 หน้าที่ของแต่ละส่วน

**Frontend**

ทำหน้าที่เป็นส่วนที่ผู้ใช้งานมองเห็นและโต้ตอบด้วย เช่น
- แสดงรายการโรงอาหาร
- แสดงรายละเอียดของร้านค้า
- แสดงรายการเมนูอาหาร
- แสดงตำแหน่งโรงอาหารบนแผนที่ด้วย Leaflet
- ส่งคำขอไปยัง Backend เพื่อขอข้อมูล

**Backend**

ทำหน้าที่เป็นตัวกลางระหว่าง Frontend และ Database เช่น
- รับคำขอจาก Frontend
- ตรวจสอบข้อมูลที่ได้รับ
- ประมวลผลคำขอ
- ติดต่อฐานข้อมูลเพื่อดึงข้อมูล
- ส่งผลลัพธ์กลับไปยัง Frontend
- จัดการข้อผิดพลาดที่เกิดขึ้นภายในระบบ

**Database**

ทำหน้าที่จัดเก็บข้อมูลทั้งหมดของระบบ โดยใช้ PostgreSQL เป็นระบบจัดการฐานข้อมูลเชิงสัมพันธ์ (Relational Database Management System)

ข้อมูลหลักประกอบด้วย
- Canteens — ข้อมูลโรงอาหาร
- Vendors — ข้อมูลร้านค้าภายในโรงอาหาร
- Menus — ข้อมูลเมนูอาหารของแต่ละร้านค้า

## 3. โครงสร้างการทำงานภายใน Backend

Backend จะถูกแบ่งออกเป็นหลายชั้น (Layered Architecture) เพื่อให้แต่ละส่วนมีหน้าที่ชัดเจน สามารถแก้ไขและพัฒนาต่อได้ง่าย

### 3.1 Routes

**หน้าที่:** กำหนดเส้นทาง API ที่ Frontend สามารถเรียกใช้งานได้

ตัวอย่าง:
- `GET /api/canteens` — เรียกดูข้อมูลโรงอาหารทั้งหมด
- `GET /api/vendors` — เรียกดูข้อมูลร้านค้าทั้งหมด
- `GET /api/menus` — เรียกดูข้อมูลเมนูทั้งหมด

Routes จะกำหนดว่าเมื่อมี Request เข้ามาที่ URL ใด จะต้องส่งต่อไปให้ Controller ตัวใดทำงาน

### 3.2 Controllers

**หน้าที่:** รับ Request จาก Routes และจัดการ Response ที่จะส่งกลับไปยัง Frontend

ตัวอย่างการทำงาน:
1. รับคำขอจาก Routes
2. อ่านค่าที่ส่งมาจาก URL หรือ Request
3. เรียกใช้งาน Service ที่เกี่ยวข้อง
4. รับผลลัพธ์จาก Service
5. ส่ง Response กลับไปยังผู้เรียกใช้งาน

Controllers ไม่ควรมีคำสั่ง SQL หรือเขียนกระบวนการประมวลผลทางธุรกิจจำนวนมากไว้ภายใน

### 3.3 Services

**หน้าที่:** จัดการกระบวนการและเงื่อนไขการทำงานของระบบ (Business Logic)

ตัวอย่าง:
- ตรวจสอบเงื่อนไขก่อนดึงข้อมูล
- ประสานงานระหว่างการทำงานหลายส่วน
- กำหนดขั้นตอนการประมวลผลข้อมูล
- ตรวจสอบว่าข้อมูลที่ต้องการมีอยู่หรือไม่

การแยก Services ออกมาช่วยให้สามารถนำกระบวนการทำงานไปใช้ซ้ำได้ และทำให้ Controllers ไม่ซับซ้อนเกินไป

### 3.4 Repositories

**หน้าที่:** ติดต่อและจัดการข้อมูลภายในฐานข้อมูล PostgreSQL

ตัวอย่าง:
- ดึงข้อมูลโรงอาหาร
- ดึงข้อมูลร้านค้าตามโรงอาหาร
- ดึงเมนูอาหารตามร้านค้า
- ค้นหาข้อมูลตาม ID

ส่วนนี้จะใช้ `pg` เป็น Database Driver สำหรับเชื่อมต่อและส่งคำสั่ง SQL ไปยัง PostgreSQL

### 3.5 Middleware

**หน้าที่:** ทำงานระหว่างที่ Request เดินทางเข้าสู่ Routes หรือก่อนส่ง Response กลับไปยังผู้ใช้งาน

ตัวอย่าง:
- ตรวจสอบรูปแบบ Request
- จัดการข้อผิดพลาด (Error Handling)
- จัดการ CORS
- บันทึกข้อมูลการเรียกใช้งาน API (Logging)

Middleware ช่วยลดการเขียนโค้ดซ้ำและทำให้สามารถจัดการกระบวนการที่ใช้ร่วมกันได้จากส่วนกลาง

## 5. การเชื่อมต่อฐานข้อมูล (Database Connection)

ระบบจะใช้ PostgreSQL เป็นฐานข้อมูลหลัก และใช้แพ็กเกจ `pg` สำหรับเชื่อมต่อจาก Backend

### 5.1 สภาพแวดล้อมในการพัฒนา

ในช่วงเริ่มต้นจะใช้ PostgreSQL ที่ติดตั้งและทำงานอยู่บนเครื่องของผู้พัฒนา (Localhost)

เหตุผล:
- สามารถใช้งานได้โดยไม่ต้องเสียค่าบริการ Hosting
- ควบคุมฐานข้อมูลและข้อมูลทดสอบได้ด้วยตนเอง
- สามารถนำไฟล์ SQL ที่มีอยู่มาใช้งานได้
- เหมาะสำหรับการพัฒนาและทดสอบ Backend ในเครื่อง

เมื่อระบบพร้อมสำหรับการนำขึ้นใช้งานจริง (Deployment) จึงค่อยพิจารณาบริการฐานข้อมูลออนไลน์ที่เหมาะสม

### 5.2 การตั้งค่าผ่าน Environment Variables

ข้อมูลสำหรับเชื่อมต่อฐานข้อมูลจะจัดเก็บไว้ในไฟล์ `.env` แทนการเขียนข้อมูลสำคัญลงใน Source Code โดยตรง

ตัวอย่าง:

```env
PORT=3000
DB_HOST=localhost
DB_PORT=5432
DB_NAME=canteens_db
DB_USER=postgres
DB_PASSWORD=your_password
```

**ข้อควรระวัง**
- ห้ามนำไฟล์ `.env` ที่มีรหัสผ่านจริงขึ้น GitHub
- ให้ใช้ `.env.example` สำหรับแสดงชื่อตัวแปรที่จำเป็น โดยไม่ใส่รหัสผ่านจริง
- ต้องกำหนด `.env` ไว้ใน `.gitignore`

## 6. แนวทางการพัฒนา API (API Development)

ระบบจะใช้ REST API สำหรับรับส่งข้อมูลระหว่าง Frontend และ Backend โดยใช้ JSON เป็นรูปแบบข้อมูลหลัก

API ในระยะแรกจะเน้นการอ่านข้อมูล (Read-only API) ได้แก่

| HTTP Method | Endpoint | หน้าที่ |
|---|---|---|
| GET | `/api/health` | ตรวจสอบสถานะ Backend |
| GET | `/api/canteens` | ดึงข้อมูลโรงอาหารทั้งหมด |
| GET | `/api/canteens/:id` | ดึงข้อมูลโรงอาหารตาม ID |
| GET | `/api/canteens/:id/vendors` | ดึงร้านค้าภายในโรงอาหาร |
| GET | `/api/vendors` | ดึงข้อมูลร้านค้าทั้งหมด |
| GET | `/api/vendors/:id` | ดึงข้อมูลร้านค้าตาม ID |
| GET | `/api/vendors/:id/menus` | ดึงเมนูของร้านค้า |
| GET | `/api/menus` | ดึงข้อมูลเมนูทั้งหมด |

รายละเอียดของแต่ละ API จะอ้างอิงจากเอกสาร `docs/api-specification.md`

## 7. การจัดการข้อผิดพลาด (Error Handling)

Backend จะต้องมีระบบจัดการข้อผิดพลาด เพื่อป้องกันไม่ให้ระบบหยุดทำงานโดยไม่จำเป็น และช่วยให้ Frontend ได้รับข้อมูลที่เข้าใจง่าย

ตัวอย่างข้อผิดพลาดที่ต้องจัดการ:
- ไม่พบข้อมูลโรงอาหารหรือร้านค้า
- ส่ง ID ที่ไม่ถูกต้อง
- ไม่สามารถเชื่อมต่อฐานข้อมูลได้
- เกิดข้อผิดพลาดระหว่างประมวลผลข้อมูล
- ส่ง Request ที่มีรูปแบบไม่ถูกต้อง

ระบบควรใช้ Middleware สำหรับจัดการข้อผิดพลาดส่วนกลาง และส่ง HTTP Status Code ให้เหมาะสมกับเหตุการณ์ที่เกิดขึ้น

## 8. ความปลอดภัยของระบบ (Security)

แนวทางด้านความปลอดภัยที่ต้องปฏิบัติตาม ได้แก่

1. ไม่เปิดเผยรหัสผ่านฐานข้อมูลหรือข้อมูลสำคัญใน Source Code
2. ใช้ Environment Variables สำหรับจัดเก็บค่าการตั้งค่าที่เป็นความลับ
3. ใช้ Parameterized Queries เมื่อส่งคำสั่ง SQL เพื่อป้องกัน SQL Injection
4. ตรวจสอบและจัดการข้อมูลที่ได้รับจากผู้ใช้งาน
5. กำหนดค่า CORS ให้เหมาะสมกับการใช้งาน
6. ไม่ส่งรายละเอียดข้อผิดพลาดภายในระบบกลับไปยังผู้ใช้งาน
7. ไม่เผยแพร่ไฟล์ `.env` ขึ้น GitHub

## 9. การเชื่อมต่อระหว่าง Frontend และ Backend

Frontend จะเรียกใช้งาน API ผ่านไฟล์ `frontend/js/api.js`

หน้าที่ของไฟล์นี้คือ
- กำหนด URL พื้นฐานของ Backend API
- ส่ง HTTP Request ไปยัง Backend
- รับข้อมูล JSON ที่ Backend ส่งกลับมา
- จัดการผลลัพธ์หรือข้อผิดพลาดที่ได้รับ

เมื่อ Backend ใหม่พร้อมใช้งาน จะต้องปรับการเรียก API จาก URL ของ AWS API Gateway เดิม ให้มาใช้ URL ของ Express Backend แทน

อย่างไรก็ตาม จะยังไม่แก้ไข Frontend จนกว่าจะตรวจสอบ API และโครงสร้างหน้าเว็บไซต์เดิมให้เรียบร้อย เพื่อป้องกันไม่ให้การทำงานส่วนอื่นเสียหาย

## 10. แผนการพัฒนาระบบ (Development Phases)

การพัฒนาจะแบ่งออกเป็นระยะ เพื่อให้สามารถตรวจสอบและทดสอบการทำงานได้ทีละส่วน

### Phase 1: วางแผนและกำหนดสถาปัตยกรรม
- ตรวจสอบโครงสร้าง Repository เดิม
- กำหนดเทคโนโลยีที่ใช้
- จัดทำเอกสาร System Architecture
- จัดทำเอกสาร API Specification

### Phase 2: เตรียม Backend
- สร้างโฟลเดอร์ Backend
- ตั้งค่า Node.js และ Express.js
- ติดตั้ง Dependencies ที่จำเป็น
- สร้างโครงสร้างไฟล์ตามสถาปัตยกรรม
- สร้าง API สำหรับตรวจสอบสถานะ Backend

### Phase 3: เชื่อมต่อฐานข้อมูล
- ติดตั้งและตั้งค่า PostgreSQL
- ตรวจสอบไฟล์ `schema.sql`
- สร้างฐานข้อมูลและตาราง
- นำข้อมูลตัวอย่างจาก `seed_data.sql` เข้าสู่ระบบ
- ตั้งค่าการเชื่อมต่อผ่าน `pg`

### Phase 4: พัฒนา REST API
- พัฒนา Routes
- พัฒนา Controllers
- พัฒนา Services
- พัฒนา Repositories
- สร้าง API สำหรับข้อมูลโรงอาหาร ร้านค้า และเมนู
- จัดการข้อผิดพลาด

### Phase 5: เชื่อมต่อ Frontend
- ปรับ `frontend/js/api.js` ให้เรียก Backend ใหม่
- เชื่อมต่อข้อมูลจาก API เข้ากับหน้าเว็บไซต์
- ปรับการแสดงผลให้ใช้ข้อมูลจากฐานข้อมูล
- ตรวจสอบการทำงานร่วมกับ Leaflet

### Phase 6: ทดสอบและตรวจสอบระบบ
- ทดสอบ API แต่ละ Endpoint
- ตรวจสอบข้อมูลที่ได้รับจาก PostgreSQL
- ตรวจสอบการทำงานระหว่าง Frontend และ Backend
- แก้ไขข้อผิดพลาด
- ตรวจสอบการทำงานโดยรวมของระบบ

## 11. ข้อกำหนดและข้อตกลงในการพัฒนา (Development Guidelines)

เพื่อให้การพัฒนาระบบเป็นไปในทิศทางเดียวกัน จะกำหนดแนวทางดังนี้

1. แยก Frontend, Backend และ Database ออกจากกันอย่างชัดเจน
2. Frontend ต้องเรียกข้อมูลผ่าน Backend API เท่านั้น ไม่เชื่อมต่อฐานข้อมูลโดยตรง
3. Backend ใช้ Node.js และ Express.js
4. Database ใช้ PostgreSQL
5. ใช้ `pg` เป็นตัวเชื่อมต่อระหว่าง Backend และ PostgreSQL
6. ใช้ REST API และ JSON เป็นมาตรฐานการรับส่งข้อมูล
7. แยก Routes, Controllers, Services และ Repositories ตามหน้าที่
8. ใช้ไฟล์ `.env` สำหรับค่าการตั้งค่าของระบบ และไม่เผยแพร่ข้อมูลสำคัญขึ้น GitHub
9. ใช้โครงสร้างฐานข้อมูลเดิมเป็นข้อมูลอ้างอิงหลัก โดยต้องตรวจสอบ `database/schema.sql` ก่อนพัฒนา API จริง
10. ไม่ใช้ AWS API Gateway เดิมในสถาปัตยกรรม Backend ใหม่
11. ตรวจสอบและทดสอบแต่ละส่วนก่อนดำเนินการในขั้นตอนถัดไป
12. พัฒนาบน Feature Branch แทนการแก้ไข `main` โดยตรง
