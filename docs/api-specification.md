# เอกสารข้อกำหนด API (API Specification)

## 1. วัตถุประสงค์ของเอกสาร

เอกสารฉบับนี้จัดทำขึ้นเพื่อกำหนดรูปแบบและมาตรฐานการสื่อสารระหว่าง Frontend และ Backend ของโครงการ CanteensWeb-TU100

โดยใช้ REST API เป็นช่องทางในการรับส่งข้อมูล และใช้ JSON เป็นรูปแบบข้อมูลหลักในการสื่อสาร

เอกสารนี้จะช่วยให้ผู้พัฒนา Frontend และ Backend เข้าใจตรงกันว่าแต่ละ API มีหน้าที่อะไร ต้องส่งข้อมูลอย่างไร และจะได้รับข้อมูลกลับมาในรูปแบบใด

## 2. รูปแบบการสื่อสารของ API

ระบบจะใช้ REST API โดยมีหลักการทำงานดังนี้

1. Frontend ส่งคำขอ (Request) ไปยัง Backend
2. Backend รับคำขอและตรวจสอบข้อมูล
3. Backend ติดต่อฐานข้อมูล PostgreSQL เพื่อดึงข้อมูลที่ต้องการ
4. Backend ส่งผลลัพธ์กลับไปยัง Frontend ในรูปแบบ JSON

**ตัวอย่าง URL พื้นฐาน**

```text
http://localhost:3000/api
```

หมายเหตุ: URL นี้เป็นตัวอย่างสำหรับการพัฒนาในเครื่อง สามารถเปลี่ยนแปลงได้ตามการตั้งค่าของระบบ

## 3. รูปแบบข้อมูลที่ส่งกลับ

API ทุก Endpoint ควรใช้รูปแบบ Response ที่เป็นมาตรฐานเดียวกัน เพื่อให้ Frontend สามารถนำข้อมูลไปใช้งานได้ง่าย

### 3.1 กรณีเรียกใช้งานสำเร็จ

```json
{
  "success": true,
  "data": []
}
```

คำอธิบาย:
- `success`: ระบุว่าการเรียกใช้งานสำเร็จหรือไม่
- `data`: ข้อมูลที่ Backend ส่งกลับมา

### 3.2 กรณีเกิดข้อผิดพลาด

```json
{
  "success": false,
  "error": {
    "message": "Resource not found"
  }
}
```

คำอธิบาย:
- `success`: มีค่าเป็น `false` เมื่อเกิดข้อผิดพลาด
- `error`: ข้อมูลเกี่ยวกับข้อผิดพลาด
- `message`: ข้อความอธิบายสาเหตุของข้อผิดพลาด

## 4. รายการ API ที่ระบบต้องรองรับ

ในระยะแรกจะพัฒนา API สำหรับการอ่านข้อมูล (Read-only API) ก่อน โดยยังไม่รวมการเพิ่ม แก้ไข หรือลบข้อมูล

### 4.1 ตรวจสอบสถานะ Backend

**Endpoint:** `GET /api/health`

หน้าที่:
- ตรวจสอบว่า Backend ทำงานอยู่หรือไม่
- ใช้สำหรับทดสอบการเชื่อมต่อกับ Backend

ตัวอย่าง Response:

```json
{
  "success": true,
  "data": {
    "status": "OK",
    "message": "Backend is running"
  }
}
```

### 4.2 ดึงข้อมูลโรงอาหารทั้งหมด

**Endpoint:** `GET /api/canteens`

หน้าที่:
- ดึงข้อมูลโรงอาหารทั้งหมดจากฐานข้อมูล
- ใช้แสดงรายการโรงอาหารบนหน้าเว็บไซต์

ตัวอย่าง Response:

```json
{
  "success": true,
  "data": [
    {
      "id": 1,
      "name": "โรงอาหาร A",
      "operating_period": "กลางวัน",
      "latitude": 14.0,
      "longitude": 100.0,
      "description": "รายละเอียดโรงอาหาร"
    }
  ]
}
```

### 4.3 ดึงข้อมูลโรงอาหารตาม ID

**Endpoint:** `GET /api/canteens/:id`

หน้าที่:
- ดึงข้อมูลโรงอาหารที่มี ID ตรงกับค่าที่ระบุ
- ใช้แสดงรายละเอียดของโรงอาหารแต่ละแห่ง

```text
GET /api/canteens/1
```

## 5. HTTP Status Codes ที่ใช้

ระบบจะใช้รหัสสถานะ HTTP เพื่อแจ้งผลการทำงานของ API ดังนี้

| Status Code | ความหมาย | การใช้งาน |
|---|---|---|
| 200 | OK | เรียกใช้งานสำเร็จ |
| 400 | Bad Request | ข้อมูลที่ส่งมาไม่ถูกต้อง |
| 404 | Not Found | ไม่พบข้อมูลที่ต้องการ |
| 500 | Internal Server Error | เกิดข้อผิดพลาดภายใน Backend |

## 6. ข้อกำหนดในการพัฒนา API

ผู้พัฒนาต้องปฏิบัติตามข้อกำหนดต่อไปนี้

1. ใช้ HTTP Method ให้เหมาะสมกับการทำงานของ API
2. ใช้ JSON เป็นรูปแบบข้อมูลในการรับส่ง
3. ใช้รูปแบบ Response มาตรฐานเดียวกันทุก Endpoint
4. แยกการทำงานของ Routes, Controllers และ Services ออกจากกัน
5. ติดต่อฐานข้อมูล PostgreSQL ผ่านส่วน Repository หรือชั้นที่รับผิดชอบการเข้าถึงฐานข้อมูล
6. ตรวจสอบค่าที่รับมาจาก URL เช่น `:id` ก่อนนำไปใช้งาน
7. จัดการข้อผิดพลาดอย่างเหมาะสม ไม่ส่งรายละเอียดภายในระบบหรือข้อมูลสำคัญกลับไปยังผู้ใช้งาน
8. ใช้ Environment Variables สำหรับจัดเก็บค่าการตั้งค่าที่แตกต่างกันในแต่ละสภาพแวดล้อม

## 7. ขอบเขตการพัฒนาในระยะแรก

ในระยะแรกจะพัฒนาเฉพาะ API สำหรับอ่านข้อมูลจากฐานข้อมูล ได้แก่

- ข้อมูลโรงอาหาร (Canteens)
- ข้อมูลร้านค้า (Vendors)
- ข้อมูลเมนูอาหาร (Menus)

ยังไม่รวม API สำหรับ:
- เพิ่มข้อมูล (Create)
- แก้ไขข้อมูล (Update)
- ลบข้อมูล (Delete)
- ระบบเข้าสู่ระบบและจัดการสิทธิ์ผู้ใช้งาน (Authentication & Authorization)

การเพิ่มความสามารถเหล่านี้จะพิจารณาในระยะถัดไปตามความต้องการของโครงการ

## 8. หมายเหตุสำหรับการพัฒนา

เอกสารฉบับนี้เป็นข้อกำหนด API เบื้องต้น (Proposed API Specification) ซึ่งใช้เป็นแนวทางในการพัฒนา Backend

ก่อนเริ่มเขียน API จริง ต้องตรวจสอบโครงสร้างตารางและชื่อคอลัมน์ในไฟล์ `database/schema.sql` ให้ตรงกับตัวอย่าง Response ในเอกสารนี้

หากโครงสร้างฐานข้อมูลจริงแตกต่างจากตัวอย่าง ต้องปรับเอกสารหรือการทำงานของ API ให้สอดคล้องกัน โดยไม่ควรคาดเดาหรือเปลี่ยนแปลงโครงสร้างฐานข้อมูลโดยไม่มีการตรวจสอบก่อน
